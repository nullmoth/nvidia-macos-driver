# NVRMFB backlight power requests

`linear-brightness` and `brightness` requests from the display slider update the user target immediately. After NVKMS applies a user request successfully, a separate low-priority callback saves the latest applied target only after two seconds without another user request. Hardware updates are not delayed. Temporary power requests and conversion probes do not restart this idle interval. A failed save is retried after two seconds without requiring another brightness event; a newer user target supersedes the old one and gets its own idle interval. Handler teardown cancels and drains the hardware callback before the save callback.

The `/options` property `nullmoth-backlight` stores three bytes: version 2 followed by the little-endian 16-bit logical target over the usable 5..100% hardware span. Legacy one-byte hardware percentages and version-1 targets remain readable: they are converted to the new range while retaining their previous rounded, floor-protected hardware output. An unchanged saved target is not written again. Older driver versions cannot interpret version-2 records. Uninstall removes this driver-owned NVRAM variable. On the next handler creation, NVRMFB reads a valid value, initializes the display parameters to it, and queues an asynchronous restore. A missing or invalid value falls back to the hardware's initial level. Every display rebind publishes the user target, even when a temporary power request last dimmed the panel. Whole-display power requests do not replace the user target; temporary dimming is not saved. A restart or teardown before the idle interval completes may retain the previous saved target.

Run `python3 tools/check_nvrmfb_backlight_target.py` for request routing and `python3 tools/test_nvrmfb_backlight_persistence.py` for extracted `withRM`, `setDisplay`, `applyFire`, and `persistFire` behavior. These checks use fixtures and do not build the kext or verify that `/options` survives a physical restart. They were updated but not rerun for this revision. On RTX 5080 Laptop/macOS 26.7, the submitter confirms that the slider spans hardware 5..100% and that the saved brightness target restores after restart. Keyboard event handling remains with macOS and is not changed by this PR.

## Parameter precision and backend limits

The four IODisplay brightness and conversion-probe parameters advertise a logical range of 0–65535. IOKit normalizes its float API using each parameter's advertised min/max; 65535 is this driver's precision choice, not an Apple-mandated range or an additional hardware capability. Both real parameter values stay synchronized after a user request. Temporary power requests do not overwrite either user value, and conversion probes only update the opposite probe.

The logical target remains unquantized through probes, pending requests and version-2 restart persistence. The final NVKMS call uses `5 + round(level * 95 / 65535)`: slider zero maps to hardware 5%, and slider maximum maps to 100%. Hardware initialization uses the inverse mapping, with hardware values at or below 5% mapping to logical zero. The 5% floor protects panels that turn completely off at zero; the affine mapping removes the old bottom 5% plateau while retaining integer-percent hardware quantization. This is a usable-range mapping, not a perceptual curve. AppleBacklightDisplay's public source uses 0..255 as its default power-brightness span when the display publishes no power-state range; that full-power request restores the saved logical target. Keyboard stepping and system volume handling are unchanged.
