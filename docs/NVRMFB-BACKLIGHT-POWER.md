# NVRMFB backlight power requests

`linear-brightness` and `brightness` requests from the display slider update the user target immediately. After NVKMS applies a user request successfully, a separate low-priority callback saves the latest applied target only after two seconds without another user request. Hardware updates are not delayed. Temporary power requests and conversion probes do not restart this idle interval. A failed save is retried after two seconds without requiring another brightness event; a newer user target supersedes the old one and gets its own idle interval. Handler teardown cancels and drains the hardware callback before the save callback.

The `/options` property `nullmoth-backlight` stores three bytes: version 1 followed by the little-endian 16-bit logical target. Legacy one-byte 0–100 values remain readable, and an unchanged saved target is not written again. Uninstall removes this driver-owned NVRAM variable. On the next handler creation, NVRMFB reads a valid value, initializes the display parameters to it, and queues an asynchronous restore. A missing or invalid value falls back to the hardware's initial level. Whole-display power requests from AppleBacklightDisplay do not replace the user target; temporary dimming is not saved. The existing 5% hardware floor remains in effect, so a saved 0% target is sent to hardware as 5%. A restart or teardown before the idle interval completes may retain the previous saved target.

Run `python3 tools/check_nvrmfb_backlight_target.py` for request routing and `python3 tools/test_nvrmfb_backlight_persistence.py` for extracted `withRM`, `setDisplay`, `applyFire`, and `persistFire` behavior. These checks use fixtures and do not build the kext or verify that `/options` survives a physical restart. The RTX 5080 Laptop/macOS 26.7 display and lid behavior were reported by the submitter; persistence across restart remains a hardware check.

## Parameter precision and backend limits

The four IODisplay brightness and conversion-probe parameters advertise a logical range of 0–65535. IOKit normalizes its float API using each parameter's advertised min/max; 65535 is this driver's precision choice, not an Apple-mandated range or an additional hardware capability. Both real parameter values stay synchronized after a user request. Temporary power requests do not overwrite either user value, and conversion probes only update the opposite probe.

The logical target remains unquantized through probes, pending requests and restart persistence. Only the final NVKMS call rounds it to integer percent and applies the existing 5% hardware floor. Logical zero remains zero in the display parameters and persistence; it must not be replaced by the clamped hardware output. Logical maximum maps to hardware 100%. AppleBacklightDisplay's public source uses 0..255 as its default power-brightness span when the display publishes no power-state range; that full-power request restores the saved logical target. No key steps, device-model branches, smoothing or perceptual curve are implemented. BrightnessKeys and macOS retain ownership of keyboard events and stepping policy. The driver does not own keyboard step size or modifier handling. A system request at or above the advertised maximum reaches logical maximum; the hardware floor applies only at the lower endpoint.

Public contracts: [Apple IODisplay float normalization](https://github.com/apple-oss-distributions/IOKitUser/blob/main/graphics.subproj/IODisplayLib.c), [IODisplay parameter handling](https://github.com/apple-oss-distributions/IOGraphics/blob/main/IOGraphicsFamily/IODisplay.cpp), and [NVIDIA integer-percent backlight](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/main/kernel-open/nvidia-modeset/nvidia-modeset-linux.c).
