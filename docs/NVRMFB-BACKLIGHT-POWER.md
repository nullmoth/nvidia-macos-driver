# NVRMFB backlight power requests

`linear-brightness` and `brightness` requests from the display slider update the user target immediately. After NVKMS applies a user request successfully, a separate low-priority callback saves the latest applied target only after two seconds without another user request. Hardware updates are not delayed. Temporary power requests and conversion probes do not restart this idle interval. A failed save is retried after two seconds without requiring another brightness event; a newer user target supersedes the old one and gets its own idle interval. Handler teardown cancels and drains the hardware callback before the save callback.

The `/options` property `nullmoth-backlight` stores three bytes: version 4 followed by the little-endian 16-bit logical target on the perceptual curve. Legacy one-byte and versions 1–3 retain their previous rounded hardware output when read. An unchanged saved target is not written again. Older drivers cannot interpret version-4 records. Uninstall removes this driver-owned NVRAM variable. On the next handler creation, NVRMFB reads a valid value, initializes the display parameters to it, and queues an asynchronous restore. A missing or invalid value falls back to the hardware's initial level. Every display rebind publishes the user target, even when a temporary power request last dimmed the panel. Whole-display power requests do not replace the user target; temporary dimming is not saved. A restart or teardown before the idle interval completes may retain the previous saved target.

Run `python3 tools/test_nvrmfb_backlight_persistence.py` to check request routing, persistence and the hardware percentages produced by the driver. These fixtures do not measure panel luminance or verify a physical restart.

## Parameter precision and backend limits

The four IODisplay brightness and conversion-probe parameters advertise a logical range of 0–65535. IOKit normalizes its float API using each parameter's advertised min/max; 65535 is this driver's precision choice, not an Apple-mandated range or an additional hardware capability. Both real parameter values stay synchronized after a user request. Temporary power requests do not overwrite either user value, and conversion probes only update the opposite probe.

The logical target retains its precision through probes, pending requests and restart persistence. The panel receives the nearest integer percent from `(8^x - 1) / 7`, where `x` is the normalized logical target. The kernel interpolates a fixed-point table and uses its inverse for hardware initialization. The panel firmware determines light output at 0%. Temporary dimming uses the previous 5–100% mapping and is capped at the current user target. AppleBacklightDisplay's public source uses 0..255 as its default power-brightness span when the display publishes no power-state range; that full-power request restores the saved logical target. Keyboard stepping and system volume handling are unchanged.

Public contracts: [Apple IODisplay float normalization](https://github.com/apple-oss-distributions/IOKitUser/blob/main/graphics.subproj/IODisplayLib.c), [IODisplay parameter handling](https://github.com/apple-oss-distributions/IOGraphics/blob/main/IOGraphicsFamily/IODisplay.cpp), and [NVIDIA integer-percent backlight](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/main/kernel-open/nvidia-modeset/nvidia-modeset-linux.c).
## Firmware that drops NVRAM writes

Some OpenCore setups (`DisableVariableWrite` without emulated NVRAM) never store runtime NVRAM writes, so `nullmoth-backlight` comes back at every restart with an old value. The installer adds a launch daemon, `com.nullmoth.backlight` (`/Library/NullMoth/backlight.sh`), that copies the variable to `/Library/NullMoth/backlight.level` every 30 seconds and at shutdown. At start it waits for the internal panel's brightness control (up to two minutes) and, only when the variable disagrees with its copy, writes the copied level and its format version to the root-only sysctl `debug.nvrmfb_backlight_restore`. The legacy bare level is interpreted as v2. Both restore paths decode older records to their previous hardware percentage. Where NVRAM keeps writes, the two agree and the daemon does nothing. NVRMFB accepts the restore only while the user has not moved the brightness this boot; a request for exactly the maximum does not count as moving it, because the display stack sends one at every start. Restores and refusals are logged to `/Library/NullMoth/backlight.log` (last 200 lines). Uninstall removes the daemon, its copy and its log. Tests: `python3 tools/test_backlight_keeper.py` (the daemon against stub `nvram`/`sysctl`, and the kernel's restore rule) and `python3 tools/test_nvrmfb_backlight_persistence.py`.
