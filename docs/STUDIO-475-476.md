# Multi-plane IOSurface VRAM sharing (#475) and deferred surface uploads (#476)

Neither change is implemented. Both alter the ordering and lifetime rules of the surface paths, and a host test can only
model a table, not the ordering. This note records what each change needs, the questions only a card can answer, and the
runs that decide them. It also lists what the related, already merged opt-in pieces give a test session to flip.

## Related pieces already in the tree (all off by default)

| Switch | What it does |
|---|---|
| `NVMTL_SURF_IMPORT_CACHE=1` | wrappers of one single-plane surface share one import of its family VRAM, kept 2 s after the last wrapper |
| `NVMTL_PLANE_SEED=1` | a seed gap caused only by our own surface-outs of other planes does not force an upload |
| `NVMTL_HOST_PAGES_SHARE=1` | wrappers of one surface share one import of its pages for the host copies |
| `debug.nvaccel_pageoff_unlocked_wait=1` | a page-off waits for the GPU without the accelerator lock, when the thread owns it once |
| `NVMTL_FC_SPEC=1` | one module per function for every function-constant set |

#475 and #476 build on these. Measure them first.

## #475: planes of one surface alias one VRAM allocation

### What the change is
Today only a single-plane surface can be backed by imported family VRAM (`nvmtl_surface_image_create` requires
`IOSurfaceGetPlaneCount(surf) <= 1`). A two-plane surface (NV12 capture and video frames) keeps one private image per plane,
uploaded from the CPU pages before it is drawn over and copied out after. The change imports the whole allocation once and
makes each plane's image a buffer alias at the plane's offset, so a plane write is a VRAM write and the CPU copies disappear.

### What it needs
1. The plugin imports the allocation with `nvmtl_vk_surface_vram(surface_id, plane, size, &buffer)`. `plane` is carried in
   the import record to NVK. It must be established what the record means for plane 1 (see the open question).
2. Per-plane images created with `nvmtl_vk_image_create_buffer_alias(..., &buffer, plane_offset, plane_row_bytes, ...)`.
   Offsets and sizes come from `IOSurfaceGetBaseAddressOfPlane`, `IOSurfaceGetBytesPerRowOfPlane` and the allocation size,
   checked for overflow and against the allocation.
3. A decision on who holds the import. All planes' wrappers must hold the same buffer, with one lifetime.
4. Synchronization that treats the allocation as one unit where the kernel does:
   - the kernel page-off takes the whole surface memory descriptor (`getMemoryDescriptor`), so a CPU lock waits for and
     copies the whole allocation, not one plane;
   - validity is kept per plane (`valid[]` bits in `nvAccelSurfDirty`), so a plane-only write must not mark another plane
     stale, and a whole-allocation copy must refresh every plane;
   - before a write that covers one plane, the other planes' pending writes must have landed, and both render-clear paths
     must do the same.
5. The surface-in tag (`nvmtl_vram_tag_*`) and the seed bookkeeping keyed by plane must be defined for planes that share a
   buffer, and `NVMTL_PLANE_SEED` must agree with it.
6. The unlocked page-off wait is a prerequisite: with the accelerator lock held through a 100 ms wait, a two-plane
   allocation stalls every other kernel call. Gate the feature on the kernel reporting that wait enabled.

### Open question that decides the design: alias or copy
When the plugin imports plane N of a shared allocation, does the kernel give back
- an alias of the same video memory the other planes use (one allocation, several offsets), or
- a separate copy of that plane's range, tracked by the family as its own resource?

The plugin's sync rules differ completely: an alias needs whole-allocation synchronization, a copy needs per-plane
synchronization and a way to keep the copies consistent. The code shows both traces: per-plane bits in the family
(`valid[6] |= 1 << plane`) and a whole-descriptor page-off. It does not show which one an import of plane > 0 produces.

How to decide it: on the test card, import both planes of an NV12 surface with the existing import switch extended to
planes, write distinct values to plane 0 and plane 1 through the GPU, read the CPU pages without any plugin copy, and run
the kernel counters (`nvaccel_surface_gpu_marks`, `nvaccel_pageoff_*`) before and after. Alias: both planes change after
one CPU lock. Copy: only the plane written last is current.

## #476: deferred imported-surface uploads

### What the change is
An upload of a locked IOSurface's pages into a GPU image (`nvmtl_vk_image_write_host`) submits a copy and waits for its
fence before returning, so the caller can release the surface lock. The change returns before the fence completes. A lease keeps
the page import and the surface lock alive, a bounded queue holds the pending uploads, and a timer retires them as their
fences signal.

### What it needs
1. A pending-upload record: image, lease on the page import, in-flight submission, fence, surface lock to release.
2. A bounded queue. At the bound, the next upload waits for the oldest (never drops it).
3. The retire step releases, in order: the in-flight submission, the lease, then the surface lock (`IOSurfaceUnlock`).
   The unlock moves from `nvmtlSurfaceIn` to the retire path, which needs the surface reference kept alive until then.
4. Orderings that must hold:
   - GPU consumers of the image are ordered after the upload by the single queue, which is true while both use the one
     queue. Any second queue or an event wait breaks it.
   - A CPU readback (`nvmtlSurfaceOut`, `nvmtl_vk_image_read*`) of the same plane waits for the pending upload first.
   - Image destroy (`nvmtl_vk_image_destroy` frees at once) waits for the pending upload first.
   - A second upload to the same image waits for the first (per-image serialization).
   - Device loss (`nvmtl_vk_note_loss`): pending uploads complete as failed and release their locks.
5. The timer runs off every caller's thread and must not hold the accelerator lock or a surface lock while it waits.

### Hazards that make it opt-in
- The surface lock is held across frames. The app that owns the surface cannot lock it for CPU writes until the upload
  retires. A frame-rate app that writes its surface every frame may stall on the lock; the bound and the retire latency
  decide whether it does.
- The retire latency is bounded by the GPU, so a busy GPU lengthens the lock.
- A leak in the retire path leaks a surface lock, which hangs the owner.

## Harness runs that decide them

Run each on the test card with the five switches above off, then on, one at a time. Keep the driver log and the kernel
counters (`nvaccel_pageoff_*`, `nvaccel_surface_gpu_*`, `nvrmfb_flip_*`) from each run.

1. NV12 upload / GPU read-back / CPU page-off, 45 frames, planes written with distinct patterns. Decides alias or copy.
2. Surface-order test, 1,100 frames: frames reach the CPU pages in submission order, none torn or repeated. Runs for both
   changes.
3. Imported-page upload with deferral, 120 frames: every deferred upload retires, the queue bound holds, the owner's lock
   latency (time from its `IOSurfaceLock` call to return) is measured per frame. Decides #476; fail it if the 99th
   percentile lock latency exceeds one frame at the panel's refresh rate.
4. Screen capture running (a recorder or Parsec encoder) with a 1080p Metal app: frames per second and `flip_us_sum /
   flip_n` with and without. The earlier cache work was observed to slow capture without the plane seed; this run covers
   that interaction.
5. Window drag at the panel's refresh rate with the capture running: WindowServer CPU per presented frame, and the count of
   imports (`family VRAM import cache` log lines).
6. A forced device loss during runs 2 and 3: every pending upload completes as failed, no surface stays locked.

## What would change the plan
- If run 1 shows copy semantics, #475 needs kernel work to keep the copies consistent, and should be redesigned rather than
  ported.
- If run 3's lock latency exceeds a frame, #476 should hold the surface lock only for the copy submission and keep a
  private snapshot of the pages for the deferred part. That costs a CPU copy and may cancel the gain.
